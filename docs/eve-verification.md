# Eve verification results (Sep 12) — reconciling the plan's "Unverified, load-bearing" list

Verified against Eve **v0.54.3**, using the framework's own version-matched docs bundled at `node_modules/eve/docs/` (authoritative) plus the compiled package source. This is the "verify first" pass from `CLAUDE.md`. Several plan/CLAUDE.md assumptions change — read this before building.

## Toolchain reality

- **Eve requires Node >= 24.** The default v22 on PATH cannot run Eve 0.54.3 (`eve` aborts: "requires Node.js >=24"). Both of us have a v24 installed under nvm but at **different patch versions**, so a hardcoded path works on one machine and silently falls back to v22 on the other. Use `nvm use 24` or `export PATH="$(ls -d ~/.nvm/versions/node/v24*/bin | tail -1):$PATH"`.
- **`eve init` refuses a non-empty directory.** It also writes its own `CLAUDE.md`/`AGENTS.md`/`README.md` and runs `git init`. We merged the scaffold into the repo root by hand: kept our project `CLAUDE.md`, saved Eve's coding-agent guide to `docs/eve-build-guide.md`, merged `.gitignore` (kept `dm/` ignored), renamed the package. `npm install` done; `eve info` reports **Compile ready, 0 errors, 10 tools**; `tsc` passes.
- App layout: app root = repo root, agent root = `agent/`. Default scaffold model is `openai/gpt-5.6-luna-fast` (set the interview/birth model deliberately via `eve set` or `agent/agent.ts`).

## The five load-bearing unknowns — resolved

### 1. Sandbox persistence — MORE persistent than assumed, but NOT durable truth
The sandbox is **not** re-seeded from git every turn. It is keyed per durable session and `/workspace` writes persist across turns, reconnects, and app redeploys (Vercel resumes after a 30-min idle timeout; Docker keeps a long-lived container). **However** the docs explicitly warn it is not reliable long-term storage: if Vercel loses the persisted snapshot, Eve silently rebuilds the sandbox from the template and **runtime-written files are lost**. "Persist important artifacts outside the sandbox." Seeding is via `agent/sandbox/workspace/**` (requires the folder layout `agent/sandbox/sandbox.ts`), mirrored 1:1 into `/workspace` at template build; adding new folders on disk works and reaches new sessions.
- **Implication:** the plan's "folder in git is state, sandbox re-seeds" is directionally right but Eve does **not** sync sandbox writes back to git for us. The midwife's `commit` step must be a real tool that writes the villager folder back to the repo (git add/commit, or write via app-runtime code). Do not treat sandbox `/workspace` as the source of truth for a birthed villager.

### 2. Runtime loading of a folder's `instructions.md` — YES, low risk
Built-in tools `read_file`, `write_file`, `bash` run with `/workspace` as cwd. The agent can read any villager folder's `instructions.md` at runtime and use it as context, and can write files at runtime (persistence caveat as in #1). Authored code can also use `ctx.getSandbox()` → `readTextFile`/`writeTextFile`.

### 3. Sessions compact or grow — COMPACT, automatically (on by default)
Compaction is on by default and triggers near the context window (default `thresholdPercent: 0.9`); Eve summarizes older turns (shortening oversized tool results first). Manual controls exist (`POST /eve/v1/session/:id/compact`, clear, reset) and `compaction.requested/completed` stream events. System-role instructions stay outside history.
- **Implication:** for core scope we do **not** need to hand-roll "restart the session and re-inject from pools." That whole caution drops to a non-issue for the hackathon.
- **Session identity:** one durable session **per Slack thread** (anchored to the first agent post's ts, resumes on later mentions), not per channel and not per message. Sessions last 30 days. The correct→approve→rerun learning loop naturally lives in one thread = one session.

### 4. Tool approval gating from Slack — NATIVE for buttons; 👍-reaction is NOT native
`defineTool({ approval: always() | once() | never() | <policy> })`. The Slack adapter **renders HITL approvals as native buttons/select menus automatically** — "you get this for free on every channel." Who may approve can be gated with an `approval.response` policy against an allowlist of `slack:TEAM:USER` ids, plus channel-level `allowedConversations`/`allowedUsers`.
- **But a 👍 emoji reaction approving a pending tool call is NOT supported.** HITL is buttons/selects only. `reaction_added` reaches only the generic `onEvent(ctx, event)` raw handler. To make 👍 approve, we must build the bridge ourselves: subscribe to `reaction_added`, detect it on the approval message, look up the pending `requestId`, and call `ctx.respond(inputResponses)`. Small but real, and the `reactions:read` scope is undocumented (add it manually).
- **Decision needed:** keep the 👍 gesture (build the bridge) vs use the free native approval **button** on camera.

### 5. `conversations.create` / posting under the villager's own name — NOT native
Eve's Slack surface is conversational (mention/DM/thread/HITL/reset). Workspace administration is absent from the documented API:
- **Post as a custom username/icon** (`chat:write.customize`): not native. `SlackPostInput` has no `username`/`icon` fields. Requires the raw escape hatch `ctx.slack.request("chat.postMessage", { username, icon_emoji, ... })` and adding the `chat:write.customize` scope. This is how a villager "posts under its own name."
- **Create a channel at birth** (`conversations.create` / `channels:manage`): not native. Raw `ctx.slack.request(...)` escape hatch + manual scope.
- **Invite users** (`conversations.invite`): not native. Same escape hatch.
- All three are buildable via `ctx.slack.request(...)` / `callSlackApi(...)`, but self-built and unscoped by the docs.

## The showstopper: NO SOCKET MODE
Eve's Slack channel is **HTTP Events API only**. There is no Socket Mode, no `SLACK_APP_TOKEN`, nowhere in the docs or package. It requires a public Request URL (`https://<host>/eve/v1/slack`) subscribed to `app_mention` + `message.im`. CLAUDE.md and the plan both say "run in socket mode locally" — **that is not possible with Eve as-is.**
Options to reach Slack:
1. **Vercel Connect** (`connectSlackCredentials(...)`) — the documented, recommended path; forwards Slack events to the agent without copying secrets into the project. Best fit if we have Vercel access.
2. **Public tunnel** (ngrok / cloudflared) in front of local `eve dev`, set as the Slack Request URL.
3. **Deploy to Vercel** (`eve deploy`) and use the deployment URL as the Request URL.
Slack setup itself: `eve add channel/slack` scaffolds `agent/channels/slack.ts`.

## Scopes we actually need (superset of the docs + our escape-hatch needs)
Documented by Eve: `app_mentions:read`, `chat:write`, `im:history`, `im:write`, `channels:history`, `groups:history`, `files:read`, `files:write`. Add for our escape-hatch features (not named by Eve, add manually to the Slack app): `chat:write.customize` (villager identity), `channels:manage` (create channel), `channels:read`, `reactions:read` (👍 bridge), `users:read`. Event subscriptions: `app_mention`, `message.im`, and `reaction_added`.

## Memory
Built-in `fileMemory()` (from `eve/memory/file`): one small document per resolved scope, recalled before each turn and after compaction, maintained by `save_memory`/`remove_memory` tools. Storage: Vercel Blob (prod) or in-memory (local `eve dev` — **not durable locally**); custom backend possible. Scope is a free-form resolver `(ctx) => string | [tenant, principal] | null`. `byPrincipal` ships built-in (per-user / DM-shaped). **Community brain (per Slack channel) and personal brain (per user/DM) are both achievable as two independent slots**, but per-channel scoping has no ready-made helper — we write a resolver that reads the Slack channel id. Note: this file-memory model is a small recalled document, not the append-only atoms/themes wiki the plan describes; the atoms/themes pool is our own layer on top (markdown files in the sandbox/repo), not `fileMemory()`.

## Net effect on the build
New work the plan under-counted, now explicit: (a) Slack connectivity without socket mode (Connect or tunnel); (b) escape-hatch Slack helpers for custom-username post, channel-create, invite; (c) the `reaction_added` → approval bridge if we keep 👍; (d) git-writeback so a birthed/edited villager folder is durable (sandbox is not truth); (e) memory scope resolvers for the two brains. What got easier: compaction is free; runtime file reads are trivial; native approval buttons are free if we don't insist on 👍.

## Deploy & Slack — proven live (Sep 12, hello-world round-trip working)
- **Slack via Vercel Connect works and is the clean path.** `vercel connect create slack --connection-method slack-app --name it-takes-a-village --triggers` provisions a **managed** Slack app (no manifest, no manually-created Slack app), opens a browser to authorize a workspace, installs it, and registers the event trigger at `/eve/v1/slack`. `agent/channels/slack.ts` references it via `connectSlackCredentials("slack/it-takes-a-village")`. This replaces the plan's earlier "build a Slack app + set the Request URL" assumption.

The connector's trigger destination is registered at connector-create time, so skipping eve's deploy wrapper loses nothing. The GitHub repo is also connected to the Vercel project, so **pushing to `main` auto-redeploys production** — the simplest path. (Consequence: a midwife `commit` that git-writes a villager folder also triggers a redeploy.)
- **Model funding, resolved.** The AI Gateway **free tier 403s premium models**; a *budget* is only a spend cap, not funds. Adding **AI Gateway credits** (we added $10) unlocks premium OpenAI and Anthropic models. `AI_GATEWAY_API_KEY` is the env var the AI SDK reads (not `VERCEL_API_GATEWAY_KEY`); it must also be set in the Vercel project's Production env for the deployment. Free ($0) models (e.g. `inclusionai/ling-3.0-flash-fin-free`) work with no credits. Current model: `openai/gpt-5.6-luna-fast`.
- **Deployment protection:** the production deployment is not behind Vercel Authentication, so Slack webhooks reach `/eve/v1/slack` (GET returns an eve JSON 404; unsigned POST returns `401 unauthorized`, i.e. the route exists and enforces Slack signature verification). ## Run-loop wiring — verified (Sep 12)

How the one app plays a different role per channel, resolved against the Eve v0.54.3 Slack channel types.

- **Channel handlers have the channel id; tools do not.** `slackChannel({ onAppMention, onMessage, onDirectMessage, onEvent })` handlers receive `message.channelId`; an authored tool's `ctx` does not carry `ctx.slack`. So channel→role routing must happen in a handler, not a tool. Handler precedence: app mention → `onAppMention` → `onMessage` → `onEvent` → built-in default.
- **Inject per-turn framing via the mention result's `context`.** `onAppMention`/`onMessage` return `{ auth, context?: string[], title? }`; `context` strings are appended to session history as user messages *before* the delivery message. This is the clean way to tell the model "act as villager X (folder, name, icon) and reply via `post_as_villager`" without a tool that can read the channel. `auth` may be `null` to dispatch a turn (we use `null`; proper attribution can be built later with `buildSlackAuthContext`). `ctx.defaultAuth` exists only on the input-response context, not on message hooks.
- **Listen vs act.** `onMessage` fires for every channel `message` event (needs `message.channels` added on the Connect trigger + `channels:history`); we call the memory-ingest seam there and dispatch a turn only when `ctx.isBotMentioned()`, `ctx.isSubscribed()` (active-thread), or `ctx.isDMOrPrivateChannel()`. Un-addressed messages return `null` (dropped, no reply) but remain in Slack history as the villager's on-demand context. `threadContext: {}` adds the recent multi-speaker transcript to each turn.
- **Reply identity caveat (to verify live):** there is no config toggle to suppress Eve's default outbound post of the model's final message. To make the reply wear the villager identity, route the whole answer through `post_as_villager` (raw `chat.postMessage` with `username`/`icon_emoji`) and instruct the model to emit **no** final assistant text; otherwise expect a double-post (generic app message + costumed villager). `SlackPostInput` has no username/icon fields, so Eve's own `thread.post` cannot customize identity.

## Sandbox credential brokering — verified shape (Sep 12)

- **Secrets stay out of the sandbox via a network-policy `transform`.** A villager's `search.sh` calls `https://api.exa.ai` with no key; the firewall injects `x-api-key`. The **authoritative object shape wraps domains in `allow:`** (the sandbox.mdx page's top-level-map example is outdated): `{ allow: { "api.exa.ai": [{ transform: [{ headers: { "x-api-key": key } }] }], "*": [] } }` (type `SandboxNetworkPolicy` = Vercel `NetworkPolicy`).
- **The object form only type-checks against a brokering-capable backend.** `DockerSandboxNetworkPolicy` is `"allow-all" | "deny-all"`, so the *default* (unpinned) backend's `use({ networkPolicy })` collapses the object to `never` and `tsc` fails. Workaround that stays clean: call `sandbox.setNetworkPolicy(policy)` on the handle returned by `use()` (its param is the full `SandboxNetworkPolicy`), and apply it only under `process.env.VERCEL` (where `defaultBackend()` resolves to the brokering-capable Vercel Sandbox). Locally, `search.sh` falls back to an `EXA_API_KEY` env var. `EXA_API_KEY` must be set in the Vercel **Production** env for brokering to work in prod.

## Reply mechanism + the loop post-mortem — verified live (Sep 12)

Hard-won, from taking the run loop live.

- **A custom-username post is NOT recognized as the app's own message.** `post_as_villager` posts via `chat.postMessage` with `username`/`icon_emoji`. Eve drops app-authored messages before `onMessage`, but it did **not** drop these, so each villager reply re-entered `onMessage`; combined with auto-continue on a subscribed thread, the villager posted in a runaway loop (50+ messages, including self-"corrections"). Fixes: (a) act ONLY on an explicit human mention — do not auto-continue on `isSubscribed()`/DMs; (b) drop bot-authored events in both `onMessage` and `onAppMention` (`author.isBot`, or raw `bot_id` / `bot_message` subtype).
- **A code deploy did not stop the live loop; pulling the installation did.** Likely the Connect trigger kept routing events to an older deployment until an uninstall/reinstall re-pointed it. Operational lesson: to hard-stop a runaway agent, remove the Eve/Connect Slack installation (kills inbound events and the bot token); `vercel connect` is not a CLI subcommand in CLI v50.9.6.
- **Do not instruct the model to emit no final text.** An empty final model message is a `turn.failed` "Empty model response", which Eve reports as an error post AND retries — producing a duplicate reply. Let the model produce a normal final message.
- **Eve's default reply renders Markdown.** `postCompletedSlackReply` calls `thread.post(message)`, and the bare-string form maps to Slack `markdown_text` (renders GitHub-flavored Markdown; 12k-char cap, longer replies upload as a `.md` snippet). So the simplest reliable villager reply is the model's **normal assistant message** — it renders, posts once, and needs no `post_as_villager`. Trade-off: it posts under the app's identity, not a per-villager name. `post_as_villager` (raw `markdown_text` with `username`/`icon_emoji`) is reserved for the birth announcement, where the per-villager name/face matters and it is a single controlled post.

## Learning-loop mechanics — verified (Sep 12), and the autonomy pivot

Verified against the sandbox/tools/memory docs while designing the write side of the learning loop.

- **Sandbox `/workspace` persists across turns within one durable session.** A durable session maps to a Slack thread. On the Vercel backend the VM idles out after ~30 min of inactivity, but Eve preserves the filesystem and resumes on the next message; Docker keeps a long-lived container (`sandbox.mdx` §Backends/§Lifecycle, line ~247). So a villager can write a file this turn and read it back next turn **in the same thread** — enough for a live "learn → obey" demo without any git round-trip. NOT durable across different threads or across redeploys; git remains the source of truth for permanence (a midwife commit re-seeds).
- **Authored tools run in the app runtime, not the sandbox — but can reach into it.** `tools/overview.mdx` (line 7): tools run in your app runtime with full `process.env`. And `ctx.getSandbox()` (line 182) returns the **live sandbox handle** (its I/O like `writeTextFile`/`readTextFile`, already bound to the turn's abort signal). So a tool *can* write regenerated memory files into the villager's sandbox — but note `compileRoomMemory` writes via `node:fs` to the app-runtime FS, not the sandbox, so a tool-based path must render contents and `writeTextFile` them in (or compile to a temp dir and copy). This is why the chosen mechanism is an **in-villager script** that runs in the sandbox via bash and touches `memory/` directly — no cross-FS copy, and it matches the "scripts do the deterministic work" rule.
- **Eve memory (`defineMemory` + provider) is turn-tied.** `recall` fires on `turn.started`, `capture` on `turn.completed` — so a provider only sees turns the villager actually takes (i.e. mentions), never passive un-mentioned chatter. `fileMemory()` is model-driven (`save_memory`/`remove_memory`), one bounded doc per scope, Blob-backed on Vercel (needs `eve add memory/file`; may cost); its scope resolver gets `channel.metadata` (channel id derivable). We are NOT using it for the community brain: the brain is git-tracked, human-readable atom files in the villager folder, and that visibility *is* the "learn in public" story — a hidden Blob doc is not.
- **PIVOT (Sep 12): autonomous memory, no confirmation gate.** The earlier design ("villager *proposes* an atom → a human confirms → it's committed after passing the fixture; humans approve by reaction") is retired for the memory layer. The villager now decides for itself what to remember and writes attributed atoms during its own turn; humans correct after the fact (a correction is a superseding atom). The line that stands: a villager autonomously manages its **memory** (atoms) but never rewrites its **code** (instructions/scripts). Consequence: the hand-built 👍-approval bridge is no longer needed for learning, and native tool-approval buttons are not used to gate it.
- **SUBSTRATE (Sep 12): Blob live + git snapshot, and the write moved out of the sandbox — see [ADR 0003](adrs/0003-memory-substrate-blob-live-git-snapshot.md).** We re-examined "git is the source of truth" for the *runtime store* and split it: **Vercel Blob** is the live memory store (cheap writes, no redeploy — the sandbox firewall blocks Blob just like git, and the app runtime has no checkout, so the earlier "record-atom.mjs writes the sandbox" mechanism could never persist beyond one thread), and **git** is a periodically-snapshotted public record. So the in-sandbox `record-atom.mjs` is **retired**: memory writes now go through an app-runtime **`record_atom` tool** over a `MemoryStore` abstraction (Blob in prod / local fs in dev), and the read side is **injected into the turn as `context`** from the store (`brainFraming` in `slack.ts`) rather than read from sandbox files. The sandbox is pure compute again (`search.sh` only). The `snapshot_memory` tool commits the readable folder to a non-deploying `village-memory` branch via the GitHub Git Data API. Net: git stays the source of truth for **code** and for the **published memory record**; **Blob** is the source of truth for **live memory** between snapshots.
